# 评估集

一份"已经确定系统该怎么表现"的具体情形清单。改代码、改 prompt、换模型之前和之后各跑一次，就知道是变好还是变坏。

## 这里有什么

| 文件 | 评什么 | 怎么跑 |
|---|---|---|
| `cases/guard.yaml` | guard 对一道菜该拦还是该放 | 随 `pytest tests/` 每次都跑 |
| `cases/duplicate.yaml` | 去重检查该不该判重复 | 随 `pytest tests/` 每次都跑 |
| `cases/evaluator.yaml` | Evaluator 的打分是否稳定、排名是否和人工一致 | `python evals/run_evaluator.py`（调真实接口，花钱） |
| `cases/feedback.yaml` | 人拒绝过一类菜之后，Evaluator 下次会不会照做 | `python evals/run_feedback.py`（调真实接口，花钱） |

前两个是确定性的，答案只有对错。后两个评的是模型，同一输入每次结果可能不同，所以要多跑几次。

`evaluator.yaml` 对应的是排名。pipeline 是按菜品分在菜系内排名、取前几名，所以看两件事：

- **稳定性**：同一道菜每次得分一样吗，在菜系里的名次变不变。不需要标签。
- **一致性**：人采纳的菜，得分是否高于人拒绝的菜。只统计有标签的菜。

脚本里的"kept"指：假如这个菜系的配额是这批菜的一半，这道菜会不会被选中。

## 怎么加一条用例

1. 遇到一个错误结论（bug、人工拒绝、自己想到的边界情况），先把"正确的结论应该是什么"写成一条用例。
2. 跑一次，确认它失败。
3. 修代码，直到它通过。

暂时不打算修的问题，在用例上写 `known_gap` 说明原因。它会以"预期失败"的方式留在清单里；哪天修好了，测试会提醒你把这个标记删掉。

`evaluator.yaml` 里现有的 10 个"拒绝"标签是**临时标签**：2026 年 5 月底开发反馈功能时在应用里录入的，不是业务方的判断。它们能用来检验"量得准不准"，不能代表"业务想要什么"。

`label` 为空的菜还没有人判断过。请业务专家填上 `accept` 或 `reject`（拒绝的写上 `reason`），并把 `source` 改成 `expert`。目前没有任何"采纳"的标签，所以排名还没法和人工对照，只能看"被拒的菜有多少次仍会被选中"。

## 跑 Evaluator 评估

```bash
python evals/run_evaluator.py                   # 每道菜评 3 次，按 Evaluator 当前配置
python evals/run_evaluator.py --thinking both   # 对比思考模式开和关
python evals/run_evaluator.py --runs 5 --preset siliconflow-deepseek-v4-flash
python evals/run_evaluator.py --thinking off --temperature 1.0   # 看 temperature 对波动的影响
```

原始结果写在 `evals/results/`（不进 git）。Evaluator 的联网搜索第一次真搜，之后回放 `evals/results/search_cache.json`，所以多次运行比较的是模型而不是搜索引擎；想刷新就删掉这个文件。

## 反馈回路（2026-10-02）

```bash
python evals/run_feedback.py              # 带反馈跑 5 次，不带跑 2 次做对照
```

把 6 条被拒记录作为反馈交给 Evaluator，再让它评 9 道没见过的菜：3 道和被拒的菜是同一类问题（应该否决），5 道普通菜（不该否决），1 道两可。这里关掉了联网搜索，所以否决只可能来自反馈。

这个评估验证的是"反馈有没有传到下一次判断"，和反馈本身对不对无关，所以用临时标签就够。

| | 提示（"要格外警惕"） | 规则（现在的写法） |
|---|---|---|
| 该否决的菜被否决 | 6 / 15 | 15 / 15 |
| 不该否决的菜被否决 | 0 / 25 | 0 / 25 |
| 5 次运行里完全正确的 | 2 次 | 5 次 |
| 否决理由里点名了对应的被拒菜 | 6 / 6 | 15 / 15 |

不带反馈时，那 3 道菜一次都没被否决（0 / 6）。

规则的写法是：逐条对照被拒理由，同样的理由成立就否决并写出对应的先例；只是食材或菜型相同不算。普通牛肉的寿喜烧丼没有因为"和牛丼被拒"而被误伤（5 次都保留）。

## 基线（2026-10-02）

`deepseek-v4-flash`，22 道菜（10 道有临时的"拒绝"标签），每种配置各评 3 次。Evaluator 只打两个菜品维度（趋势热度、小贩替代性），总分由代码计算。

| | 思考开 | 思考关 |
|---|---|---|
| 同一道菜的分数波动（中位数） | 5.9 分 | 4.2 分 |
| 3 次之间"选中/没选中"发生变化的菜 | 4 / 22 | 4 / 22 |
| 有时否决、有时不否决的菜 | 0 | 1 |
| 临时标签里被拒的菜仍被选中 | 9 / 30 次 | 9 / 30 次 |
| 每批耗时 | 9 秒 | 5 秒 |
| token（输入 + 输出） | 84k + 37k | 48k + 21k |
| 联网搜索次数 | 27 | 6 |

读这张表时注意：

- 两种配置的稳定性差不多。一个维度差 1 分（满分 10）就是总分 4 到 6 分，所以波动基本就是某个维度差了 1 分。
- 思考开会更多地去搜索验证。两道疑似编造的菜（Kyoto Purple Sweet Potato Don、Gyeongju Hwangnam Bread Bowl），思考开时 3 次都否决；思考关时前者从未被否决，后者 3 次里否决 2 次。
- 临时标签里因成本和复杂度被拒的和牛丼、鳗鱼三吃，两种配置下每次都排在日料前列。现有两个维度都偏向高档、少见的菜；成本和复杂度该不该成为维度、怎么定义，要业务方来定。
- 还没有"采纳"的标签，排名和人工是否一致现在无法检验。

### 改成"配额 + 排名"之前的发现

同一天早些时候，Evaluator 还在打三个维度（含按菜系给分的蓝海）、并用 80 分线和自动降线判定通过。当时测到的几件事促成了现在的设计：

- 蓝海分是菜系的固定值。历史上各菜系的菜品部分得分几乎一样（满分 60，都在 43 到 47），总分差距全部来自蓝海，所以 80 分线对墨西哥菜形同虚设，对其他菜系几乎过不去。
- 通过线降到 65 时，每道菜分数不变，但临时标签里被拒的 10 道中放行的从 2 道变成 8 道。
- 模型自己加总分会出错：新马菜系那批被报成 3.25 而不是 32.5。
- 思考模式下 temperature 不生效。思考关时把 temperature 从 0.1 调到 1.0，分数波动中位数从 0 升到 4.0 分。
